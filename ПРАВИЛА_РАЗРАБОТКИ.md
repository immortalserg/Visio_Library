# Правила разработки проекта Visio_Library

## 1. Назначение проекта

Проект предназначен для хранения, разработки и сопровождения библиотек фигур Microsoft Visio (VSSX), а также для создания инструментов повторного использования вложенных фигур и их обновления при изменении исходных мастеров.

Главная техническая задача — обеспечить прослеживаемую связь между исходным маленьким мастером и его копиями, включёнными в состав более крупных мастеров.

Вся документация, комментарии, инструкции, сообщения программы и пользовательские интерфейсы проекта ведутся на русском языке. Имена файлов, программные идентификаторы, имена полей форматов и стандартные технические термины могут оставаться на английском языке, если это необходимо для совместимости.

## 2. Архитектура библиотек

### 2.1. Центральная библиотека исходных мастеров

В проекте используется одна центральная библиотека исходных мастеров (далее — Центральная библиотека).

В ней хранятся оригинальные небольшие мастера, предназначенные для повторного использования в других фигурах и библиотеках.

Правила:

- Центральная библиотека является единственным авторитетным источником исходных мастеров.
- Новые исходные маленькие мастера создаются и редактируются в Центральной библиотеке.
- Каждому исходному мастеру вручную назначается постоянный уникальный короткий идентификатор в ячейке User.LMID.
- Переименование мастера не должно менять его идентификатор.
- Производные библиотеки не должны становиться альтернативными источниками оригиналов.
- Экспериментальные файлы и библиотеки должны быть явно обозначены как тестовые и не должны автоматически считаться источниками истины.

### 2.2. Производные библиотеки

Производные библиотеки содержат крупные мастера, в состав которых могут входить копии мастеров из Центральной библиотеки.

Например, библиотека ABB может содержать крупный мастер выключателя, внутри которого находится копия маленького мастера vint.

Правила:

- Вложенная копия должна сохранять идентификатор исходного мастера.
- Имя вложенной фигуры не используется как надёжный идентификатор происхождения.
- Локальный Shape ID не используется как глобальный идентификатор: его значение ограничено конкретной XML-структурой.
- Наличие одинакового идентификатора в разных производных библиотеках является нормальным: это разные экземпляры одного исходного мастера.
- Производная библиотека не должна самостоятельно назначать новый идентификатор исходной фигуре при обычном обновлении.

## 3. Идентификация и происхождение фигур

### 3.1. Постоянный короткий идентификатор

Для каждого исходного мастера вручную задаётся короткий уникальный идентификатор в пользовательской ячейке ShapeSheet User.LMID.

Примеры значений:

- vint
- abb_sh201l
- switch_1p

User.LMID — это технический идентификатор происхождения мастера, а не отображаемое название. Его значение выбирает и задаёт разработчик при создании мастера.

Правила:

- идентификатор создаётся и назначается вручную один раз при регистрации исходного мастера;
- значение должно быть уникальным в пределах Центральной библиотеки;
- идентификатор не должен автоматически формироваться из Name или NameU;
- переименование мастера или файла не меняет User.LMID;
- идентификатор переносится во все зависимые копии;
- значение нельзя повторно использовать для другого исходного мастера;
- имя фигуры, локальный номер Shape ID и путь к файлу не заменяют User.LMID.

UUID для идентификации исходных мастеров в проекте не используется.

### 3.2. Где хранить идентификатор

Предпочтительный вариант — пользовательские данные ShapeSheet, например пользовательская ячейка User.LMID, либо пользовательское свойство ShapeSheet.

Окончательный способ хранения выбирается только после проверки на реальных файлах Visio.

Обязательная проверка:

1. Добавить идентификатор исходному мастеру.
2. Скопировать мастер внутрь другого мастера.
3. Сохранить библиотеку в Visio.
4. Закрыть и повторно открыть файл.
5. Проверить, сохранился ли идентификатор во вложенной фигуре.
6. Повторить проверку после копирования, перемещения и редактирования фигуры.

До успешного завершения проверки нельзя считать автоматический перенос пользовательских данных гарантированным. Если Visio не переносит идентификатор, инструмент проекта должен внедрять его после вставки либо использовать другой проверенный механизм.

### 3.3. Дополнительные сведения

Для исходного мастера рекомендуется хранить:

- User.LMID — постоянный короткий идентификатор;
- User.LMVersion — понятная человеку версия;
- LibrarySource — логическое имя Центральной библиотеки или источника;
- контрольный хэш содержимого — для точного обнаружения изменений.

Хэш вычисляется по нормализованному содержимому, относящемуся к геометрии и структуре мастера. Изменения форматирования XML, порядка атрибутов или служебных данных не должны без необходимости приводить к ложному изменению хэша.

## 4. Манифест Центральной библиотеки

В Центральной библиотеке должен быть предусмотрен файл манифеста manifest.json.

Манифест служит индексом и описанием исходных мастеров. Он не заменяет идентификатор, встроенный в фигуру.

Для каждого мастера рекомендуется хранить:

- LMID;
- внутреннее имя мастера;
- отображаемое имя;
- путь к VSSX и/или XML-части;
- текущую версию;
- хэш геометрического содержимого;
- сведения о совместимости и примечания.

Манифест должен проверяться на корректность JSON, уникальность LMID и существование указанных мастеров. Если данные в манифесте расходятся с содержимым VSSX, инструмент должен сообщать об ошибке, а не молча выбирать один из вариантов.

## 5. Правила обновления зависимых фигур

Сборщик обновлений должен использовать Центральную библиотеку как единственный каталог оригиналов.

Общий алгоритм:

1. Прочитать и проверить манифест Центральной библиотеки.
2. Построить индекс исходных мастеров по LMID.
3. Открыть выбранную производную библиотеку.
4. Найти зарегистрированные большие мастера и проверить их вложенные фигуры.
5. Считать User.LMID каждой зависимой фигуры.
6. Найти оригинал по LMID в индексе Центральной библиотеки.
7. Сравнить версию и/или хэш исходного содержимого с данными, сохранёнными у зависимой фигуры.
8. При обнаружении изменений подготовить обновление.
9. Проверить результат и сохранить библиотеку.

Сборщик не должен выполнять глобальный поиск оригиналов по всем доступным VSSX-файлам. Отсутствие LMID в Центральной библиотеке должно приводить к понятному предупреждению или ошибке, а не к поиску случайной фигуры с похожим именем.

### 5.1. Сохранение локальных параметров

Обновление геометрии не должно автоматически сбрасывать параметры экземпляра, которые относятся к его размещению внутри родительской фигуры.

По возможности необходимо сохранять:

- положение и координаты;
- угол поворота;
- отражение по горизонтали и вертикали;
- масштаб и локальные размеры, если они не являются частью обновляемой геометрии;
- связи и формулы, относящиеся к родительской группе;
- пользовательские изменения оформления.

Перед заменой необходимо разделять данные исходного мастера и локальные данные экземпляра. Нельзя без проверки заменять весь XML-узел фигуры целиком.

### 5.2. Оформление и пользовательские изменения

По умолчанию обновление не должно уничтожать пользовательские изменения цвета, заливки, линии, текста и других свойств экземпляра.

Для этого необходимо определить перечень свойств, которые обновляются из оригинала, и перечень локальных свойств, которые сохраняются. Правила слияния должны быть явными и документированными.

Пользователь должен иметь возможность отключить обновление отдельного экземпляра или зафиксировать его текущее состояние. Такой экземпляр не должен изменяться автоматически.

### 5.3. Безопасность обновления

- Перед массовым обновлением создаётся резервная копия исходной библиотеки.
- Сначала выполняется проверка и формируется отчёт о предстоящих изменениях.
- Ошибки отдельных фигур должны быть отражены в отчёте.
- При невозможности безопасного обновления фигура пропускается, а исходные данные сохраняются.
- После обновления файл должен оставаться корректным VSSX, открываться в Visio и сохранять связи и ресурсы.

## 6. Работа с форматом VSSX и XML

VSSX является пакетом Office Open XML. При работе с ним необходимо учитывать взаимосвязи XML-частей и ресурсов пакета.

Правила:

- Не изменять XML изолированно от связанных файлов и relationships.
- Не удалять неизвестные элементы, атрибуты, пространства имён и отношения без доказанной необходимости.
- Сохранять изображения, встроенные объекты, стили, темы и прочие ресурсы.
- Учитывать, что идентификаторы Shape ID и Master ID имеют локальную область действия.
- Не полагаться на порядок элементов XML как на постоянный идентификатор.
- При изменении структуры проверять ссылки и отношения внутри пакета.
- Не считать два XML-файла эквивалентными только на основании совпадения имён или визуального вида.

При чтении и записи XML необходимо сохранять совместимость с файлами, созданными Microsoft Visio. Любые предположения о поведении Visio подтверждаются тестовыми файлами.

## 7. Разработка инструментов

- Логика разбора VSSX, поиска зависимостей, сравнения и обновления должна быть разделена на самостоятельные компоненты.
- Операции чтения не должны изменять исходные файлы.
- Изменения выполняются на копии или в явно выбранном выходном файле.
- Ошибки должны содержать имя файла, мастера, LMID и причину сбоя, если эти сведения доступны.
- Повторный запуск без изменения исходных данных не должен приводить к дополнительным изменениям (идемпотентность).
- Для потенциально разрушающих операций предусматриваются проверка, резервная копия и понятный отчёт.
- Не добавлять неподтверждённые обходные решения без описания ограничений.

## 8. Тестирование

Для каждого значимого изменения необходимо проверять как минимум:

1. Чтение исходной Центральной библиотеки.
2. Чтение производственной библиотеки с вложенными фигурами.
3. Поиск зависимостей по LMID.
4. Поведение при неизвестном UUID.
5. Поведение при дублирующемся LMID в манифесте.
6. Обнаружение изменения исходной геометрии.
7. Обновление вложенной фигуры.
8. Сохранение положения, поворота и отражения.
9. Сохранение локального оформления.
10. Сохранение целостности VSSX и открытие результата в Microsoft Visio.

Тестовые библиотеки должны включать случаи с несколькими одинаковыми экземплярами одного исходного мастера, разными локальными параметрами, переименованными фигурами и отсутствующими источниками.

Тесты должны отделять проверку XML-структуры от проверки фактического поведения Microsoft Visio. Успешный разбор XML сам по себе не доказывает, что Visio корректно откроет и сохранит результат.

## 9. Документация и язык проекта

Вся пользовательская и техническая документация проекта ведётся на русском языке.

Это правило распространяется на README и инструкции, описания архитектуры, правила разработки, комментарии в исходном коде, сообщения программы и диагностические отчёты, примеры использования, описания тестов и известных ограничений.

Исключения допускаются для обязательных идентификаторов форматов, имён API, библиотек, команд, ключевых слов языков программирования и общепринятых технических обозначений.

Новые технические решения должны сопровождаться кратким объяснением: что изменено, зачем, какие ограничения существуют и как проверить результат.

## 10. Работа с Git

- Изменения должны быть небольшими и логически завершёнными.
- Сообщения коммитов должны кратко описывать суть изменения.
- Не включать в коммиты временные файлы, кэш, резервные копии и локальные настройки среды разработки.
- Не перезаписывать исходные библиотеки без необходимости и без возможности восстановления.
- Изменения структуры каталогов и формата манифеста документировать.
- Перед отправкой изменений проверять состав коммита и отсутствие случайно добавленных файлов.

## 11. Принцип принятия технических решений

Если поведение Microsoft Visio, формат XML или перенос пользовательских данных не подтверждены экспериментом или документацией, это должно быть обозначено как предположение.

Нельзя строить критически важную функциональность на неподтверждённом поведении. Сначала создаётся минимальный воспроизводимый тест, затем фиксируется результат и только после этого принимается архитектурное решение.

Приоритеты проекта:

1. Сохранность исходных библиотек и данных.
2. Надёжная идентификация происхождения фигур.
3. Предсказуемое обновление зависимостей.
4. Сохранение локальных параметров и пользовательского оформления.
5. Совместимость с Microsoft Visio.
6. Простота сопровождения и расширения проекта.
